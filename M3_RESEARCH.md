# M3 GPU research for the navigation trainer

**Scope.** This note answers which Apple GPU features are real on this machine, where they fit this code, and what to measure next. It uses current Apple documentation and the local Metal kernels. Claims about speed remain hypotheses until the end-to-end trainer confirms them.

## What the machine and API support

The local machine reports Apple M3 and 16 GB unified memory. The repository uses runtime-compiled MSL with `MTLMathModeSafe` and precise floating-point functions. The active developer directory is Command Line Tools; `xcodebuild` and the `metal` compiler tool are absent. Runtime Metal work may still run, but Xcode’s shader cost graph and GPU capture are not available until Xcode is installed.

Apple maps M3 GPUs to **Apple GPU family 9**. The current feature table places M3 in Apple9 and lists SIMD-scoped matrix multiply and reduction from Apple7 upward. MSL’s 8×8 `simdgroup_matrix` operations are therefore supported on M3. The API is cooperative: every thread in the SIMD group must take part, and its lane-to-element mapping is unspecified. Use `simdgroup_float8x8` and `simdgroup_multiply_accumulate` as a measured FP32 path; do not assume a CUDA-style tensor core, a fixed matrix lane map, or an automatic speedup. Apple’s A14-to-Metal family 7 talk shows the 8×8 MSL operation and a 16×16 tiled example. [Apple feature tables](https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf) · [Apple A14 Metal Tech Talk](https://developer.apple.com/videos/play/tech-talks/10858/) · [Metal Shading Language specification](https://developer.apple.com/metal/Metal-Shading-Language-Specification.pdf)

**Metal Performance Primitives (MPP) is a separate path.** Apple’s MPP guide describes the Metal 4 tensor API and MPP as a way to use the M5 GPU neural accelerators. The feature table lists Metal 4 tensor APIs beginning at Apple7, but that alone does not show that M3 has M5’s accelerator or that MPP will accelerate this workload on M3. Do not rely on MPP here unless the local SDK accepts the API, the device reports support, and a same-shape benchmark beats both MSL and MPS. The guide’s M5 tile sizes and tuning rules are M5-specific. [Apple MPP Programming Guide](https://developer.apple.com/download/files/Metal-Performance-Primitives-Programming-Guide.pdf)

The useful M3-specific feature is Apple’s **dynamic shader-core memory** (often marketed with Dynamic Caching). Apple says Apple9 allocates and releases register storage over a SIMD group’s lifetime and dynamically shares on-chip storage across register, threadgroup, tile, stack, and buffer data. This can improve occupancy when a kernel has uneven register demand. It does not remove the cost of long-lived local arrays, guarantee a fixed occupancy, or give the app a cache-allocation knob. The local code has a concrete candidate: `sim_act` copies 660 observation floats into `thread float obs[660]` for every environment; standalone actor forward does the same. That is 2,640 bytes of per-invocation local state before the other arrays. Pass a device pointer into the scalar helper and remove the copy first. Then measure. [Apple M3 GPU architecture talk](https://developer.apple.com/videos/play/tech-talks/111375/)

M3’s FP16 pipeline is also relevant. Apple says FP16 instructions run at peak throughput, need fewer registers, and reduce bandwidth when buffers are stored as FP16. Apple9 can overlap FP16, FP32, and integer instructions across SIMD groups. This supports a controlled mixed-precision experiment; it does not establish that an entire PPO update can safely use half precision. Preserve FP32 optimizer state and accumulation until parity and learning curves support a change. The current safe math mode is the right baseline. Metal’s `MTLMathModeFast` permits transformations that may violate IEEE 754, so compare it as a separate numerical variant after profiling shows math functions are material. [Apple M3 GPU architecture talk](https://developer.apple.com/videos/play/tech-talks/111375/) · [Metal compiler math mode](https://developer.apple.com/documentation/metal/mtlcompileoptions/mathmode)

## What the current workload suggests

The actor forward is a matrix-vector operation with weights `[64,660]` and 660-float observations. Training naturally batches 256 observations, so it can become a matrix-matrix operation `[64,660] × [660,256]`; this is a better fit for 8×8 cooperative matrix work than one environment per matrix. The 660 input width has a four-element tail beyond an 8-element tile. Compare a masked tail with padding to 664. Keep the current row-major parameter format as the scalar baseline, then test a layout that lets each tile reuse weights across several samples. Make every SIMD-group call uniform. Check results against the current FP32 reference before timing.

The backward pass has the same GEMM shape: a `[64,batch]` hidden-delta matrix times `[batch,660]` observations produces the `[64,660]` first-layer gradient. A direct tiled reduction can avoid materializing one gradient per parameter per sample. The old partial-gradient layout is `[parameter,batch]`: backward writes are contiguous across sample lanes, but the old reduction assigns one thread to a parameter and walks the batch serially. At batch 256, the actor partial buffer alone is about 43 MB. The PPO worker is already replacing this path with hidden deltas and direct GEMM-style gradients; benchmark that algorithm before adding a second reduction design.

The RAPTOR kernel has a small 22→16 layer, a 16-unit GRU, and a 16→4 output layer. SIMD-group tiling across environments could help these batched affine transforms, but the recurrent state still advances sequentially within each environment. A separate probe reported 238 million RAPTOR steps/s at 32,768 environments. The full loop reports about 141,000 navigation steps/s at 128 environments, while the PPO update takes 4.33 seconds per 4,096-row rollout. Treat these as run-specific measurements, not hardware limits. PPO is the first target; return to RAPTOR only if per-kernel timing shows it matters.

The current simulator traces 320 rays per environment against a room and up to eight analytic box, sphere, or cylinder obstacles. M3 hardware ray tracing is real, but it accelerates Metal acceleration-structure intersection APIs. It will not accelerate the current analytic `wray` loop by itself. Building acceleration structures for small, moving, per-environment obstacle sets may cost more than the intersections. Keep the analytic kernel unless scene-size sweeps show a crossover.

All current buffers use `MTLStorageModeShared`. On Apple silicon, shared storage lets the CPU and GPU access the same system-memory resource; it still requires synchronization before the other processor reads changes. Test `Private` storage for rollout and scratch buffers that only the GPU needs, with explicit staging for checkpoints or evaluation. Shared memory avoids an explicit copy; it does not prove equal GPU throughput. [Shared storage mode](https://developer.apple.com/documentation/metal/mtlstoragemode/shared)

The C++ wrapper currently creates one compute encoder for every dispatch, then closes it. Each rollout step encodes depth, observation, actor, and advance dispatches in one command buffer and does not wait on the CPU between them. First test one ordinary compute encoder with those ordered dispatches; bind each pipeline’s arguments as needed. Keep tracked resources and ordered dispatches. If using concurrent dispatch, untracked heaps, or ICB resources, add the documented resource barriers/fences and check results. GPU-wide barriers inside an MSL kernel do not exist; threadgroup barriers cannot synchronize separate threadgroups into a safe persistent training loop. Apple supports compute indirect command buffers from Apple3 upward, so M3 can run them, but this fixed graph may not benefit because the host already batches work in a single command buffer. [Compute encoder](https://developer.apple.com/documentation/metal/mtlcomputecommandencoder) · [Metal resource synchronization](https://developer.apple.com/documentation/metal/resource-synchronization) · [GPU-encoded indirect commands](https://developer.apple.com/documentation/metal/encoding-indirect-command-buffers-on-the-gpu)

## Ranked experiments

Set a baseline with the same seed, scenario mix, PPO epochs, batch size, observation fidelity, and held-out evaluation. The acceptance metric is **wall time to the same held-out success threshold**. Keep an optimization only when it improves that metric or fixes a correctness or capacity limit. A practical first gate is at least a 10% reduction in complete rollout-plus-update time, with no material loss in held-out success; then confirm time-to-threshold over matched runs. Do not accept a faster microbenchmark alone.

| Rank | Probe | Measurement and pass condition |
|---|---|---|
| 1 | Remove the 660-float thread-local observation copies. Compare the device-pointer scalar forward and the current copy path at batch 1, 128, and 256. | CPU/Metal actor outputs remain within the existing FP32 tolerance. Record forward latency, complete PPO update time, register/stack or local-memory evidence if available, and end-to-end time-to-threshold. This is small and low-risk. |
| 2 | Implement an 8×8 MSL SIMD-group matrix baseline for batched actor forward and first-layer gradient. Compare scalar, tiled FP32, then mixed FP16 operands with FP32 accumulation/state. | Validate outputs, gradients, PPO loss, and Adam against reference before performance. Sweep batch 128/256/512; test the 660→664 tail. Keep only if full PPO update and complete learning reach threshold sooner. Check MSL support at runtime using `device.supportsFamily(.apple7)` or the platform equivalent. |
| 3 | Sweep compute threadgroup sizes for each pipeline using multiples of that pipeline’s `threadExecutionWidth`; test 32/64/128/256 only when legal and include `maxTotalThreadsPerThreadgroup`. | Measure per-kernel median GPU time at N=1, 128, 2,048, and 8,192. Do not hardcode a presumed SIMD width. Apple explicitly says it varies by GPU and recommends querying the pipeline. [Thread width](https://developer.apple.com/documentation/metal/mtlcomputepipelinestate/threadexecutionwidth) · [Pipeline thread limit](https://developer.apple.com/documentation/metal/mtlcomputepipelinestate/maxtotalthreadsperthreadgroup) |
| 4 | Keep all rollout dispatches on a single ordinary encoder; separately compare one batched command buffer with a reusable compute ICB only if host encoding time is significant. | No CPU wait per step. Confirm each producer-consumer result is correct. ICB earns its complexity only if command encoding is a measured part of complete training time. |
| 5 | Compare `Shared` and `Private` for GPU-only rollout/scratch storage; later compare FP16 observation storage after validating PPO and learning. | Record memory footprint, full rollout/update time, checkpoint/evaluation staging time, and time-to-threshold. The 16 GB machine’s row-major rollout observation buffer alone is `N × horizon × 660 × 4` bytes. At N=8,192 and horizon 32, this is about 0.69 GB; at N=32,768 it is about 2.77 GB. |
| 6 | Compare safe math with fast math; compare MPS matrix multiplication and the current scalar kernel for the exact actor/critic shapes. Use `vDSP_mmul` as the CPU matrix baseline. | Check FP32 parity, actor action drift, PPO stability, and complete time-to-threshold. MPS is a credible GPU library baseline; Accelerate is a credible CPU baseline. Keep either only if its end-to-end wall time wins. [MPS matrix multiply](https://developer.apple.com/documentation/metalperformanceshaders/mpsmatrixmultiplication) · [Accelerate `vDSP_mmul`](https://developer.apple.com/documentation/accelerate/vdsp_mmul) |

### Counters without Xcode

The app can query Metal counters itself. Enumerate `device.counterSets` and each set’s `counters`; Apple warns that individual devices may expose only some counters. Query `supportsCounterSampling` at the desired boundary. Create an `MTLCounterSampleBufferDescriptor` for a supported timestamp, statistic, or stage-utilization set, with shared storage if the CPU will resolve it. Sample immediately before and after a named dispatch, finish the command buffer, call `resolveCounterRange`, then interpret the result using the matching result type. For timestamp results subtract adjacent `MTLCounterResultTimestamp.timestamp` values. This gives runtime hardware counter evidence without opening Xcode, when the M3 driver exposes the requested set. Keep `GPUStartTime`/`GPUEndTime` and CPU wall time as fallback. Counter support is queried, not assumed; the public pipeline API does not expose a register-count property. [Counter sets and samples](https://developer.apple.com/documentation/metal/gpu-counters-and-counter-sample-buffers) · [Resolve counter data](https://developer.apple.com/documentation/metal/converting-a-gpus-counter-data-into-a-readable-format)

## Bottom line

The most actionable M3-specific fact is Apple9’s dynamic shader-core memory: it makes high-register kernels more viable, while the local 660-float copy is still an obvious lifetime and local-storage cost to remove. The most promising compute feature is MSL’s supported 8×8 SIMD-group matrix multiply, applied to batched PPO forward and gradients. MPP/M5 neural acceleration is not established on this M3. Shared unified memory, runtime GPU counters, FP16 execution, compute ICBs, and hardware ray tracing are real capabilities, but each needs a workload-specific test. The next useful evidence is a complete PPO-update and held-out time-to-threshold comparison, not a peak FLOP claim.
