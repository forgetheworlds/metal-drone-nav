# Training scale review — 2026-10-07

Scope: static source/code review of the current phase; no training, GPU or Webots jobs were run. The objective remains fast, reliable local 3-D navigation through the actual RAPTOR-to-motor path, with combined capabilities, retention, robustness and eventual independent transfer. This is not a completion review.

## Blocking findings

1. **The proposed environment-count pilot is a PPO batch-regime experiment, not a pure hardware comparison.** At 4,194,304 transitions, horizon 32 and two epochs, N=128 performs 1,024 policy collection/update cycles with 32 Adam steps each; N=8,192 performs 16 cycles with 2,048 Adam steps each. Equal 32,768 Adam steps do not make these equivalent. Later updates use data collected by an increasingly old policy. Advantage normalization covers different populations, and only contiguous minibatch blocks are shuffled: at N=128 a 256-row batch spans two ticks; at N>=512 it can fit inside one tick. See `main.mm:1321–1379`. Run the pilot, but label its cause correctly. Log KL/clip fraction if available, and inspect learning/retention alongside throughput. A poor large-N result does not establish that experience scale fails.

2. **Capacity cannot safely be changed with a macro alone.** `sim.metal:230,327` allocate `hidden[64]`, but the critic routine writes `PPO_HIDDEN` entries. `main.mm:559` correctly rejects the fused actor outside width 64; its Metal implementation uses eight fixed hidden tiles (`ppo.metal:194`). Selecting the scalar actor does not repair the simulator scratch arrays. `ppo.hpp:28,42` also shares the actor and critic hidden width, so a width sweep changes both capacities. Fix and verify these owning paths before capacity training. Report actor and critic counts separately. Hold critic width fixed for an actor-capacity claim, or explicitly call the experiment joint actor/critic capacity.

3. **A larger policy lacks an equivalent launch state.** `navigation_training.hpp:39` requires the exact actor parameter count. Its special critic migration at lines 44–57 only handles the old 32-input, 64-hidden critic. Comparing pretrained small actors against random larger actors confounds capacity with prior training. Use a documented function-preserving widening with nonidentical extra units, prove actor means/log probabilities and critic values match on retained observations, and reset optimizer state consistently. Alternatively train every size from scratch on the same direct mixture, with the pretrained baseline reported separately. Parameter-space anchor strength is not automatically equivalent after widening; the same represented function can have a different parameter distance and gradient scale.

## Fix interpretation and measurement before selecting a winner

- **Phase balance helps but does not equalize experience.** `navigation_scale_banks.py:15–21` rotates bank order. Larger N covers more initial phases while each learner lane completes fewer episodes. The 2,048 unique records remain unchanged. Compare the phase-balanced N128 arm against the other phase-balanced arms, not only against legacy ordering. The current counter (`navigation_critic_training.mm:83–90`) records local episode slot after rotation, not original task identity. Thus a flat slot histogram cannot establish balanced family/difficulty exposure. Retain the rotation mapping and count source identity or family/difficulty transitions and episode attempts, split by clean/delayed lanes. Episode-length weighting also changes transition exposure.
- **Evaluation cadence must use samples or elapsed training time.** `navigation_critic_training.mm:1502` schedules evaluation in rollouts. A common `--eval-every 50` gives many observations at N128 and only the final one at N8192 in this pilot. This changes selection opportunity and evaluation overhead. Use common transition checkpoints; show training-only time and end-to-end time separately. The built-in DEV call at lines 1507–1509 uses zero sensor/command delay and `.best` optimizes that score. It cannot select a robust combined winner alone. Evaluate fixed checkpoint choices across clean, delay, static, short-open and longer-course retention suites.
- **Warmstart semantics are explicit and useful.** Lines 1350–1364 load actor and critic, reset Adam, override log standard deviations, and capture the anchor afterward. Apply these operations identically to both source T parents and all arms. Their success is evidence of matched continuation, not continuation of the old optimizer trajectory.
- **Do not rename the existing priority score “competence.”** `challenge_training.hpp:162–195` uses mean absolute raw GAE, then ranks it with staleness within fixed family quotas (lines 319–358). Large value error can identify noise or unlearnable tasks. Keep this as a separate control if reused. The simplest competence sampler should use TRAIN-only recent success and change in success per capability/difficulty band, minimum visit counts, a broad uniform floor and explicit retention mass. Do not use held-out DEV outcomes to select individual training tasks.
- **Keep reward fixed during the N pilot.** The current local reward recipe is in `navigation_critic_training.mm:484`. Before adding long/detour or short-TTC task mass, require feasible reference returns to beat hovering, straight collision and unsafe shortcuts under the actual discount and time budget. Then test learned behavior. Offline return ranking alone cannot establish a better navigator.

## Minimum decisive sequence

1. Finish the four-N pilot with common sample checkpoints and source-identity exposure summaries. Measure collection/update cost, peak process and Metal memory, useful task coverage, and all retention gates. System-wide GPU utilization includes browser work. Use this pilot to choose two practical regimes, not to declare a scaling law.
2. Continue those two regimes with matched seeds from both T parents and enough experience for repeated task cycles. Keep reward, corpus, actor, anchor and delay mixture fixed. Plot capability and retention against both transitions and training hours. Reject a throughput winner that reliably loses capability per hour.
3. At the selected regime, compare direct mixed training with one simple competence sampler using the same corpus and budget. Preserve a broad sampling floor. Fix checkpoint selection in advance. Repeat across seeds before attributing gains to ordering. Increase unique corpus diversity as its own subsequent axis.
4. Run the capacity sweep only after the scratch-buffer, kernel, critic-width and launch-equivalence controls above pass. With the current one-hidden-layer 184-input/4-output actor, trainable parameter count is `189*H+8`; widths near 264, 792, 2645 and 5291 approximate the requested sizes. Confirm compiled counts rather than relying on labels. Larger teachers do not prove future distillation, quantization or ESP32-S3 latency/memory feasibility.

## Supported versus unproven

`results/training-scale/preflight.json` reports full default100 checkpoint byte parity and N512 training with fixed N128 evaluation. These support the narrow environment-count/evaluation plumbing change. They do not validate N8192 learning, phase-balanced coverage, a capacity variant or a curriculum.

The source baseline still fails static-C and short-open retention gates. The completed native flight count reported by the parent is not an independently audited transfer result. `STATUS.md` still records the older 112/192 handoff and no-live-jobs state; update it when publishing this phase's results so it cannot mislead the next operator. No evidence reviewed here establishes combined deployment readiness or a fundamental architecture limit.
